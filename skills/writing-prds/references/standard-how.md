# 標準：Part 2 要怎麼做

Part 2 是做的人每天看的部分。標準只有一個：工程師、設計師或半年後接手的人，不用再問任何人，就知道要做成什麼樣、怎樣算完成。

## 2.1 產品用戶

列出實際操作系統的角色。每個角色三到五句：什麼時候用、做哪些事、哪些事不能做。

- [ ] 角色名稱和名詞解釋一致，和系統畫面上的字一致。
- [ ] 每個角色的權限邊界寫得出來（看得到誰的資料、能不能核准自己的東西）。
- [ ] 一個人可以同時是兩種角色時，寫明以哪個為準。

## 2.2 流程

先給一張主線流程，讓讀者看到全貌，再進模組。

- 從「他遇到的第一步」開始，不從登入開始。
- 判斷一定寫成可以回答是或否的句子。
- 不只一個角色或系統在動作，用泳道圖；前端跳轉複雜，用頁面流程圖並給畫面編號。
- 有檢查或擋下的地方，在圖上標出來：擋住（不能繼續）、提醒（可以繼續但要確認）、紀錄（只留下痕跡）要分得出來。

- [ ] 每一步都有主詞：誰做、或系統做。
- [ ] 每個判斷的兩條路都有去處，沒有走到一半不見的線。
- [ ] 圖上的步驟名稱和模組頁的標題對得起來。

## 2.3 功能模組與優先級

一張總表，讀者只看這張就知道這一版做什麼。欄位：模組編號｜模組名稱｜功能點｜描述｜優先級或階段｜狀態｜（需要時）負責人、備註。

- 描述寫行為，不寫技術做法。「送出時擋下重複的時段」，不寫「加一個唯一索引」。
- 優先級要有依據：為什麼這個先做（有日期壓力、其他功能依賴它、風險最高）。
- **只列有人要的功能。** 使用者說的、會議決定的、既有系統已經有的，才進這張表。寫的時候想到值得加的（對方只說了送出和核准，你想到還該有撤回），不要直接加成功能點：列在決定紀錄的「建議加，未列入範圍」，寫明為什麼值得做，由對方決定。對方說「先做最基本的」時更要守住。流程少了這一步就走不通時，在流程上標「待確認」，連到那一列建議。
- 篇幅跟著系統走，不設上限也不湊數。功能多的系統，文件本來就長；小系統不用為了看起來完整而多寫。

- [ ] 每一列對得到一個模組頁的一節。
- [ ] 每個功能點一句話，讀得出「做了之後畫面或行為哪裡不一樣」。
- [ ] 沒有「其他」「雜項」這種裝不下的列。
- [ ] 表上每個功能點都指得出是誰要的；自己想到的在「建議加，未列入範圍」。

## 模組頁：需求詳述

每個模組一頁。開頭一段話說這個模組解決什麼，接一張功能點的小表（編號、狀態、階段），再逐一寫。

三種版型，預設用 B：

- **A 極簡**：需求很小，圖旁邊直接寫兩三句。
- **B 上圖下文**（八成的情況）：上面放畫面，互動點標上號碼 1、2、3；下面照號碼逐條寫。每一條寫元件名稱，再寫顯示文字、類型、格式限制、驗證、點了之後怎樣、成功與失敗各顯示什麼。
- **C 大表格**：規則很多而且彼此獨立時才用，容易變成閱讀負擔。

寫法擇一，挑團隊習慣看的：功能需求（「系統…」，編號列）、使用者故事（作為…我想要…以便…，加主要流程與例外）、驗收條件（什麼情況算成功，編號列）。

- 抽象的規則一定配一個實際的例子，用具體的值。「金額差超過兩成時提醒」後面接「上次 11,204，這次 15,000（+34%）會提醒；12,500（+12%）不會」。
- 和設計有關的要求，寫出為什麼要這樣（設計意圖），之後有人想改時才判斷得了。
- 現在的畫面和之後的畫面不同時，左右並排，各放一張。

- [ ] 每個互動點都說了成功和失敗各會怎樣。
- [ ] 每條規則至少有一個具體值的例子。
- [ ] 文字、按鈕名稱和畫面上的一字不差。
- [ ] 沒有「視情況」「適當地」「等等」。

## 特殊情況

每個模組最後列出：情況 → 畫面顯示什麼 → 系統做什麼。至少想過這幾種：資料還沒有、資料不完整、同一件事做兩次、兩個人同時做、沒有權限的人來做、做到一半取消、之後才發現做錯要回頭。

- [ ] 每一種都寫了使用者看到什麼字，不是只寫「報錯」。
- [ ] 回頭的路寫清楚：誰可以退回、退回後資料變成什麼狀態。

## 驗收條件

每個模組一份，編號列。每一條是一個可以實際操作、只有過或不過兩種結果的句子：在什麼情況下、做什麼、看到什麼。

> 3. 同一個時段第二個人送出預約：畫面顯示「這個時段已經有人訂了」，並列出是誰訂的；沒有新增任何預約。

- [ ] 每個功能點至少一條。
- [ ] 每個「擋住」和每個「提醒」各有一條。
- [ ] 測的人不用問寫的人，就能照著做一遍。

## 狀態與階段

功能模組表和每個模組頁都標：**已上線**（現在就有，這版不變）、**要改**（已有，這版修改）、**新增**、**待確認**（還要有人決定）。分階段做時再標第幾階段，以及是否已經上測試環境或正式環境。

讀者最常問的是「這個現在有沒有」。把現況和計畫混在一起寫，是文件失去信任最快的方式。

## 實作之後

做出來和寫的不一樣時，改文件，不要讓文件停在計畫。在模組頁加一節「實作時的決定」：原本的寫法、實作、原因；同時在修訂追蹤表記一列。還沒驗證的也照實寫（「沒有在真的手機上看過」）。

## 整個 Part 2 的檢查

- [ ] 主線流程走一遍，每一步都找得到對應的模組頁。
- [ ] Part 1 的每個痛點，在這裡找得到解法。
- [ ] 同一個名詞在各頁寫法一致。
- [ ] 隨便翻一個模組頁，五分鐘內看得懂要做什麼、怎樣算完成。
