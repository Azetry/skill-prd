# 標準：語氣與用詞

PRD 是工作文件。讀的人想快點知道要做什麼；寫得像廣告或像 AI 產生的摘要，讀者會開始懷疑內容。

## 語氣

- 平實、直接，像一個熟悉產品的同事在說明。先講結論，再講理由。
- 每個句子要有主詞：誰做、系統做什麼。
- 短句。一句話講一件事。
- 有主張。該建議就建議，並說為什麼；不要把選項攤開就停。
- 不確定的事照實說：「還沒驗證」「這是假設」。不要用模糊的字帶過。
- **不追究人。** 描述問題時寫流程和畫面哪裡容易讓人走錯，不寫誰做錯了。也不要貶低現有的設計；現在的做法通常有它的理由，這一版是在它之上改進。
- 給主管或其他部門看的章節（首頁、Part 1），用他們的詞，不用工程的詞。

## 該避免的寫法

| 避免 | 原因 | 改成 |
|---|---|---|
| 賦能、無縫、一站式、打造、全方位、強大 | 沒有資訊 | 寫它實際做的事 |
| 提升效率、優化流程、改善體驗（後面沒有對象和數字） | 無法驗證 | 誰的、哪一段、從多少到多少 |
| 「不僅…更…」「不是…而是…」 | 繞一圈才講重點 | 直接講重點 |
| 破折號插入語、冒號後才揭曉的句子 | 讀起來做作 | 拆成兩句 |
| 反問句（「為什麼這很重要？」） | 像簡報講稿 | 直接寫原因 |
| 每節結尾再總結一次 | 重複 | 刪掉 |
| 表情符號當作項目符號或標題裝飾 | 分散注意 | 只在重現真實畫面上的字時保留 |
| 粗體到處都是 | 等於沒有重點 | 一段最多一處 |
| 視情況、適當地、等等、相關 | 把決定丟給讀者 | 寫出是哪些情況 |
| 值得注意的是、綜上所述、總而言之 | 填充 | 刪掉 |

## 用詞

- 同一件事只用一個詞。挑定之後整份文件、畫面、訊息都用它，並收進名詞解釋。
- 用產品畫面上真的出現的字。按鈕叫「送出」，文件就不要寫「提交」。
- 用讀者所在地的說法。台灣的文件用台灣的用語：資料、檔案、設定、登入、訊息、網路、軟體、預設、支援。
- 數字帶單位，金額帶幣別，日期寫完整（跨年時加年份，並寫星期幾）。
- 英文縮寫第一次出現時寫全稱或中文。

## 來源沒說的，當場標出來

文件裡的每一條規則、數字和畫面文字，都要回得去某個來源：使用者說的、會議紀錄寫的、程式實際做的。寫的時候常常要補來源沒提的細節（字數上限、邊界怎麼算、失敗時顯示哪一句），不補就寫不完整。可以補，但讀者要看得出哪些是補的：

- 在那一句的旁邊標 `<span class="status ask">待確認</span>`，並在決定紀錄加一列：問題、你的建議、找誰決定。
- 只寫在回覆或 `notes/` 裡不算數。讀文件的人看不到那些地方，會把補的當成已經決定的事照著做。
- 會讓做的人做出不同東西的才要標。段落怎麼排、示範資料用哪個名字，這類寫法上的選擇不用標。
- 對方回答之後，把標記拿掉，決定紀錄那一列搬到「已決定」。

## 資料

- 人名、公司、帳號、電話、金額一律用示範資料，並在文件開頭或該頁註明。
- 真實的數字（用量、人力、成本）可以寫，但要有來源。
- 帳號、證號類即使是示範資料，也只顯示部分。

## 檢查

- [ ] 大聲念一段，聽起來像人在說明，不像新聞稿。
- [ ] 隨便挑三個句子，都找得到主詞和動作。
- [ ] 搜尋「提升」「優化」「改善」，每一處後面都有對象和依據。
- [ ] 沒有責怪人或貶低現狀的句子。
- [ ] 同一個名詞沒有兩種寫法。
- [ ] 每一條自己補的規則，旁邊都有「待確認」，而且決定紀錄找得到。
