# 審查：拿著標準看成品

寫的人看自己的東西，幾乎都會覺得沒問題。審查交給另一個沒看過寫作過程的人：他只拿到成品和標準，站在讀者的位置看。

## 什麼時候審

- 每一站寫完、給使用者看之前，審這一站的產出物。
- 整份文件要交付之前，把 Part 1 和 Part 2 一起再審一次，看前後有沒有對起來。
- 小修改（改幾個字、加一列修訂）不用審，跑 `scripts/check_prd.py` 就好。

## 怎麼交給審查者

能開 subagent 時，開一個新的，只給它下面這些。路徑都寫完整路徑：審查者不知道這個 skill 在哪裡，也不知道使用者的專案在哪裡。不要給它對話紀錄、訪談過程或你的想法；它知道得越少，越像真正的讀者。

```
你是這份產品需求文件的審查者。請站在讀者的位置看，不要幫忙改寫。

讀者：<誰會看、看完要做什麼>
要審的檔案：<完整路徑>
標準：<這一站對應的 standard-*.md 的完整路徑>，以及 standard-writing.md 的完整路徑

做法：
1. 先只讀要審的檔案，寫下讀完之後你認為「這份文件要做什麼、怎樣算完成」。
2. 再讀標準，逐條對照檔案。
3. 照下面的格式回報。每一項都要指出檔案和段落，並引用原文。

回報格式：
## 我讀到的重點（三到五句）
## 必改（不改，讀者會做錯或無法判斷）
- <檔案>〈<段落標題>〉：「<原文>」→ 違反哪一條標準 → 建議怎麼改
## 建議改（改了更好）
## 做的人還會想問的問題（文件沒回答的）
## 通過的部分（一行）

沒有問題就說沒有，不要為了有東西寫而挑毛病。
```

開審查者時，模型和 effort 用這份 PRD 的 `prd.json` 裡 `roles.reviewer` 寫的（沒有就用 `fable`／`high`）。

不能開 subagent 時：先去做別的事，回來後只打開成品和標準，照同樣的格式自己寫一份，存成 `notes/review-站<N>.md`。不要邊看邊改；先把問題列完再動手。交付時要明說這一站只有自我審查、沒有獨立審過，讓使用者知道哪裡值得自己多看一眼。

## 拿到回報之後

1. 「我讀到的重點」和你想說的不一樣，代表文件沒把事情講清楚。先修這個，其他都是次要的。
2. 「必改」全部處理。不同意的，在回覆裡寫出理由，不要默默略過。
3. 「做的人還會想問的問題」逐題決定：補進文件、去問使用者，或列進決定紀錄。
4. 改完重跑 `scripts/check_prd.py`，再審一次。

## 出口：最多兩輪，然後交給人

同一站最多審兩輪。第二輪審完還有「必改」，就停手，交給使用者。沒有出口的循環會一直繞；兩輪都過不了，通常不是再改一次能解決的，而是少了一個事實或決定、標準本身不清楚，或兩條要求互相牴觸。這些只有人能決定。兩輪是預設，使用者說要多或少就照他的。

交接時不要只把兩份回報貼上去。對方沒看過過程，要讓他不翻紀錄就能決定：先講這一站要完成什麼，再講卡在哪裡、為什麼卡，最後收在要他決定什麼。照這個格式：

```
## 交接：站 <N>「<產出物>」審了兩輪，還有 <幾> 項沒過

**這一站要完成什麼**：<這份產出物給誰看、要讓他能做什麼>
**現在的狀態**：<已經過的部分一句帶過；還卡著哪幾項>

### 卡住的第 1 項
- **在哪裡**：<檔案>〈<段落>〉，原文：「<引用>」
- **要求是什麼**：<哪一份標準的哪一條，或審查者的原話>
- **第一輪**：<我怎麼改> → <審查者為什麼不過>
- **第二輪**：<我怎麼改> → <審查者為什麼還是不過>
- **卡住的原因**：<缺事實或決定／標準不清楚／兩條要求互相牴觸／我和審查者判斷不同，選一個並說明>
- **要你決定**：<選項 A 與後果；選項 B 與後果；我的建議>

### 不用你決定、但你可能想知道的
<沒卡住的小問題、順手發現的事；沒有就不寫>
```

每一項都要引用原文，並寫出兩輪各自的改法和沒過的理由；只寫「審查沒過」等於沒交接。

對方決定之後照著改，重跑檢查。改動沒有超出他決定的範圍，就不用再開審查者。同一類原因卡住第二次，建議對方把答案補進對應的標準檔，下次就不會再卡。

## 審查者最常抓到的問題

- 規則沒有例子，或例子沒有具體的值。
- 來源沒說的規則寫成了定案，頁面上沒有「待確認」。審查者拿得到來源（會議紀錄、使用者的原話）時，逐條對回去。
- 只寫了成功的情況，沒寫失敗時畫面顯示什麼。
- 現況和計畫混在一起，看不出哪些已經有了。
- 名詞前後不一致。
- 一頁全是字，沒有圖。
- 目標無法驗證。
- 數字沒有來源。
- 句子裡找不到是誰做。
