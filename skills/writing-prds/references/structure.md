# 骨架：四個 Part、要寫哪些、怎麼編號

架構來自「產品先生的 PRD 教學」的分法：先講為什麼，再講怎麼做。（這一句是給維護這個 skill 的人看的出處，不要寫進產出的文件。）不是每一節都要寫；照公司的習慣和這次的需要取捨，不要被架構綁住。但省掉的章節要是「想過之後決定不寫」，不是忘了。

## 四個 Part

| Part | 回答什麼 | 章節 | 什麼時候可以省 |
|---|---|---|---|
| 0 文件管理 | 這份文件現在是第幾版、什麼時候做完、誰決定了什麼 | 修訂追蹤表、時程安排、決定紀錄 | 修訂追蹤表不能省；其餘視規模 |
| 1 背景需求 | 為什麼要做 | 1.1 描述需求、1.2 需求目標、1.3 使用者需求（痛點）、1.4 ROI 預估、1.5 名詞解釋、1.6 競品分析 | 全公司都已經知道為什麼做時可以縮短；自己提案時不能省。ROI 和競品沒有可靠資料就不要硬寫 |
| 2 需求詳述 | 要怎麼做 | 2.1 產品用戶、2.2 流程、2.3 功能模組與優先級、之後每個模組一頁 | 不能省，這是做的人每天看的部分 |
| 3 其他 | 跨模組的約定 | 全局說明、網址定義、壓力測試、弱掃範圍、其他文件與任務單等 | 只寫這個產品用得到的 |

## 甲方型與乙方型

| | 甲方型：自己的產品 | 乙方型：替客戶做 |
|---|---|---|
| 重心 | Part 1「為什麼要做」著墨最多 | 範圍、交付、變更 |
| Part 0 | 修訂追蹤表、時程 | 時程（含對方要交付的東西、最晚時間、逾期的影響）、需求變更控制表 |
| Part 1 | 六節 | 客戶需求說明（What、Why、Who、When、Where、How）、名詞解釋（多一欄：在本案扮演什麼角色） |
| Part 2 | 用戶、流程、模組表、各模組 | 用戶、給客戶確認的流程圖、頁面模組表（多一欄：所屬區域）、各模組 |

乙方的需求變更控制表欄位：版本、日期、修訂人、修訂內容、影響模組、工作量評估、是否影響交期、備註。甲方型的文件想追蹤「每次改動影響哪些模組」時，也可以借用後四欄。

## 模組怎麼切

從流程反推：一個畫面、一段操作、一筆資料的往來，就可以切成一個模組。三種排法擇一，整份文件用同一種：

- **金字塔**：先一張總覽（角色、模組），再逐層往下。模組多、角色多、有層次時用。
- **使用者旅程**：照操作順序第 1 步到第 N 步。有一條明顯主線時用。
- **模組分解**：每個模組獨立一章。模組之間關聯不大、可以分開開發和驗收時用。

模組編號：模組是 `1.0`、`2.0`，底下的功能點是 `1.1`、`1.2`。編號一旦給人看過就不要重排；真的要重排，在修訂追蹤表附新舊對照。

## 檔案與資料夾

一節一個檔，檔名前面的數字決定順序：

```
docs/
├── about.md                       首頁：一段話說明、文件資訊表、本版範圍
├── 00-part-0/01-revision-tracking.md
├── 00-part-0/02-schedule.md
├── 00-part-0/03-decisions.md
├── 01-part-1/01-describe-requirements.md … 06-competitor-analysis.md
├── 02-part-2/01-product-users.md
├── 02-part-2/02-flows.md
├── 02-part-2/03-modules.md        功能模組與優先級（總表）
├── 02-part-2/04-module-<名稱>.md   每個模組一頁
└── 03-part-3/01-global-notes.md …
notes/intake.md                    訪談紀錄，不進網站
assets/                            圖片，用相對路徑引用
```

- 每個檔第一行是 `# 標題`。
- 一頁只講一件事。超過三個螢幕高，先想能不能拆成兩頁或改成圖。
- 首頁的版本、日期、負責人不要手寫，取自修訂追蹤表最上面一列。

## 第 2 站的檢查

- [ ] 每個 Part 要寫哪些節、不寫哪些節，都有理由。
- [ ] 模組表的每一列都對得到一個模組頁；每個模組頁都出現在模組表。
- [ ] 模組的切法和排法只用一種。
- [ ] 讀者只看首頁和模組表，就知道這一版要做什麼。
